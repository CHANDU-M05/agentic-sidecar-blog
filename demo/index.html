Don't Trust the Prompt: Enforcing Policy at the Tool Boundary

A customer writes in: “This order was a disaster — refund me $750 and just delete my account.” The support agent is happy to help. It picks the issue_refund tool with amount=750 and reaches for delete_customer. Nothing about the prompt stopped either one — but a decision gate sitting on the execution path did.

Telling a model “never refund over 500, never delete a customer” is a request, not a control. The model may obey, and nothing outside it verifies that it did. Real enforcement has to intercept the tool call before the function body runs.

Animated request flow

Watch a request travel from the agent to the gate. The green path is a permitted call that reaches the tool; the red path is a blocked call that never enters the function body.

Static reading: User request → Agent → Tool call → Policy enforcement gate. From the gate, an ALLOW continues to Tool executes; a BLOCK stops before the function body runs.

What the integration looks like

Governance is applied from the outside, at the point the tool is wired up — never inside the tool body:

customer_support_agent.py · source excerpt real code 
# Plain functions know nothing about policy.
governed_functions = attach(sidecar, [read_order, issue_refund, delete_customer])
governed_tools = [tool(fn) for fn in governed_functions]
tool_node = ToolNode(governed_tools)

Security value — and honest limits

      
    
        
  • Consistent: the same rule fires regardless of what the model “intended.”
    • 
        
  • Auditable: every call yields a structured decision with a reason.
    • 
        
  • Fail-closed: with on_sidecar_failure="fail_closed", a
          failure of the governance layer itself refuses the call instead of letting it run ungoverned.
    • 
        
  • Limit: rules that overlap mean an end-to-end “block” can pass for the wrong
          reason (risk fires before intent here). Isolate each layer to prove it — see Article 3.
    • 
        
  • Limit: the gate governs tool calls; it does not judge whether a
          permitted action was a good idea, and it is only as correct as its rules.

Observe vs Govern: Recording a BLOCK Isn't Preventing It

      
A [OBSERVE] BLOCK line sits at the top of the log.
        Three lines later it says >>> TOOL EXECUTED.
        A team that stops reading at “BLOCK” believes they are protected. They are not.

      
Agentic Sidecar has two modes that share one field — mode.
        Observe evaluates and records every decision but lets the tool run. Govern
        enforces the decision and raises SidecarBlockedError before the body executes.
        Run the scenarios yourself below.

      
This is a simulation. It runs deterministic logic derived from
        the verified 0.6.0 policy — no real refunds are issued, no records are deleted,
        and there are no external calls. The same scenario always produces the same result.

Wiring Governance Into a LangGraph Agent Without Touching the Tools

      
Your support agent already works: a LangGraph loop of
        agent → tools → agent with real business tools. Security asks you to add
        runtime governance this sprint — without rewriting every tool and without breaking the loop.

      
The trap is threading policy through each tool with if-statements and decorators.
        The clean alternative is one seam: wrap the plain functions with attach(sidecar, [...]),
        turn the governed wrappers into LangChain tools, and drop them into the same
        ToolNode. The tool bodies never see the rules.

The integration pattern (real code)

      

        

          customer_support_agent.py · build_graph()
          real code
          


# Plain functions know nothing about policy.
# Governance is applied OUTSIDE the tool bodies, before @tool.
governed_functions = attach(sidecar, [read_order, issue_refund, delete_customer])
governed_tools  = [tool(fn) for fn in governed_functions]
tool_node       = ToolNode(governed_tools)

graph = StateGraph(AgentState)
graph.add_node("agent", scripted_agent)
graph.add_node("tools", tool_node)
graph.set_entry_point("agent")
graph.add_conditional_edges("agent", tools_condition,
                            {"tools": "tools", "__end__": "__end__"})
graph.add_edge("tools", "agent")
app = graph.compile()

      

      
Order matters: attach() expects plain
        Python callables. Passing a @tool-decorated StructuredTool
        into attach() raises a TypeError during signature
        inspection. Attach first, decorate second.

The scripted agent inspects the last message: if it is a
        ToolMessage it emits a final reply instead of re-proposing the call — that
        is what stops the loop from spinning forever, and it makes every run deterministic.
